css-console — Phase 3 manual testing

Source discovery, identity, linked stylesheets, raw sources, gating, exclusion, and the scan lifecycle, exercised through the one public entry point: createCSSConsole().

How to use this document

Serve the repository with vp dev and open http://localhost:5173/manual-testing-phase3.html (any port works). Each scenario has a Load button that fills the playground: the markup, the raw sources, and the instance options. Press Run scan and compare the event stream and the summary against the expectations. Opened from file://, the page degrades to reading mode.

Two things are different from the Phase 2 document. First, the playground drives the public facade, so a scan collects sources from the whole document — there is no root option on createCSSConsole(). This page therefore styles itself through document.adoptedStyleSheets, which discovery does not read, so the only <style> and <link> elements a scan finds are the ones the loaded scenario put on the stage. Second, an instance is kept alive across Run scan presses and is recreated only when the options, the raw sources, or the New instance button change it — source identity lives per instance, and several scenarios depend on that.

The stage markup is re-applied only when the markup field changed since the last run. That is deliberate too: identity continuity (scenario 2.6) needs the same live elements across two scans, and re-injecting the markup would replace them with new ones.

1. The facade

    

      createCSSConsole() is the whole public API: construct with configuration,
      subscribe() for live events, scan() for a summary carrying every
      record and diagnostic, and dispose() when done. Construction is side-effect free
      beyond validation — nothing reads the document until scan().

2. Inline sources and identity

    

      An anonymous <style> is named style-<hash> from its
      content; an author can name one with the data-css-console-source attribute, and
      that name is honored verbatim. Identity is visible in the stream as the probe-start's source
      URL: inline:<id>. The scanner never writes to the document, so generated
      names are never stamped onto elements.
    


    

      

        
2.1 An anonymous style is named by its content hash

        
        
      

      

        
<style>
/* css-console: log color */
.anon { color: rgb(7, 7, 7); }
</style>
<p class="anon"></p>

        

          Expected
          
    
            
  • The probe-start's source URL is inline:style-<hash>.
    • 
            
  • 
              Run again, and press New instance and run once more: the name is
              identical every time, because the hash depends only on the CSS text. Reload the page
              and run again — still the same name. That is what keeps reports comparable across page
              loads.
            
    • 
          

        

      

    


    

      

        
2.2 The identity attribute wins, verbatim

        
        
      

      

        
<style data-css-console-source="brand tokens (v2)">
/* css-console: log color */
.branded-source { color: rgb(9, 0, 9); }
</style>
<p class="branded-source"></p>

        

          Expected
          
    
            
  • 
              The probe-start's source URL is inline:brand tokens (v2) — the value is
              not trimmed, normalized, prefixed, or hashed. An author who names a source is naming
              it for a report they intend to read.
            
    •

/* css-console: log color */
.unnamed { color: rgb(5, 5, 5); }
</style>
<p class="unnamed"></p>

        

          Expected
          
    
            
  • 
              The source is named inline:style-<hash>, exactly as if the
              attribute were missing — an empty string is not a request for an empty identifier,
              which would make every report about this source illegible.

2.4 Two byte-identical anonymous styles: a positional suffix

</style>

          Expected
          
    
            
  •

              second inline:style-<hash>-2. Identical content hashes identically;
              the counter is positional, by document order within one discovery.
            
    •

2.5 A duplicated author identity is reported, never repaired

<p class="dup-a"></p><p class="dup-b"></p>

3. Linked stylesheets

    

      A <link rel="stylesheet"> is discovered, fetched, and named by its resolved
      URL — no hash needed, because a URL is already stable across reloads. One failing link never
      affects another source: fault isolation is by source. The fixture links below carry Vite's
      ?direct query because the dev server answers a plain .css path with
      a JavaScript module wrapping the CSS; ?direct returns the stylesheet text, the
      same convention the browser test suite pins.
    


    

      

        
3.1 A linked stylesheet becomes a source named by its URL

        
        
      

      

        
<link rel="stylesheet" href="/manual-testing-phase3.css?direct">
<p class="linked-probe"></p>

        

          Expected
          
    
            
  • 
              One record: color: rgb(20, 40, 60), label linked, from the
              probe-start whose source URL is the absolute
              http://…/manual-testing-phase3.css?direct.
            
    • 
            
  • 
              Summary sources: { discovered: 1, compiled: 1, failed: 0, excluded: 0 }.
            
    • 
          

        

      

    


    

      

        
3.2 A mixed-case rel is still a stylesheet

        
        
      

      

        
<link rel="StyleSheet" href="/manual-testing-phase3.css?direct">
<p class="linked-probe"></p>

        

          Expected
          
    
            
  • 
              Identical output to 3.1. Link relationship keywords are ASCII case-insensitive and the
              engine applies this stylesheet, so discovery matches it too — even though the DOM's
              own relList.contains("stylesheet") answers false for it,
              because relList is token-exact.
            
    • 
          

        

      

    


    

      

        
3.3 An HTTP error is a diagnostic, not a crash

        
        
      

      

        
<link rel="stylesheet" href="/phase3-no-such-file.css">
<style>
/* css-console: log color */
.survivor { color: rgb(4, 4, 4); }
</style>
<p class="survivor"></p>

        

          Expected
          
    
            
  • 
              One SOURCE_HTTP_ERROR diagnostic, error severity, details carrying
              status: 404, statusText: "Not Found", and the absolute URL.
              No location — a transport failure has no CSS position.
            
    • 
            
  • 
              The inline style still compiles and its record still arrives. Summary sources:
              { discovered: 2, compiled: 1, failed: 1, excluded: 0 }.
            
    • 
          

        

      

    


    

      

        
3.4 An unreachable host fails without attributing a cause

        
        
      

      

        
<link rel="stylesheet" href="https://css-console-phase3.invalid/x.css">
<p>nothing to probe</p>

        

          Expected
          
    
            
  • 
              One SOURCE_LOAD_FAILED diagnostic with details
              error: "TypeError", followed by the diagnostic's own message naming the
              likely causes and pointing out that none can be attributed with certainty.
            
    • 
            
  • 
              The TypeError is the browser's, not TypeScript's: the Fetch specification
              rejects an unmakeable request with a TypeError carrying no detail,
              precisely so a page cannot probe why a request was blocked. A cross-origin block, a
              CSP restriction, and a network failure are therefore indistinguishable from inside the
              page. The details record that engine fact verbatim rather than replacing it with a
              friendlier guess; the message beside it does the explaining. Check the network panel
              for the real cause.
            
    • 
            
  • 
              Summary sources: { discovered: 1, compiled: 0, failed: 1, excluded: 0 }.
            
    •

4. Raw sources

    

      A caller can hand CSS to the scanner directly: rawSources is an array of
      { id, css } objects, scanned beside the discovered sources — or instead of them,
      with sources: "none". A raw source's probes still match the live document,
      because what is scanned and what is matched are different questions.
    


    

      

        
4.1 A raw source is scanned and matches the live document

        
        
      

      

        
<p class="raw-target">matched by a raw source</p>

        
[{ "id": "tokens", "css": "/* css-console: log margin-left */\n.raw-target { margin-left: 6px; }" }]

        

          Expected
          
    
            
  • The probe-start's source URL is raw:tokens.
    • 
            
  • 
              One record with margin-left: 0px — not the authored 6px. A
              raw source is described to the scanner, never applied to the page, so the element
              really has no margin, and the resolved value is what the live element computes. The
              authored 6px is still in the record's raw JSON (toggle it on) as the
              value's authored field. Scanned and applied are different things, and
              this scenario is the proof.
            
    • 
            
  • 
              Summary sources: { discovered: 1, compiled: 1, failed: 0, excluded: 0 }.
            
    • 
          

        

      

    


    

      

        
4.2 sources: "none" scans only what the caller supplied

        
        
      

      

        
<style>
/* css-console: log color */
.ignored-by-scan { color: rgb(6, 6, 6); }
</style>
<p class="ignored-by-scan raw-target"></p>

        
[{ "id": "only-me", "css": "/* css-console: log color */\n.raw-target { color: rgb(11, 12, 13); }" }]

        
{ "sources": "none" }

        

          Expected
          
    
            
  • 
              The inline style on the stage is invisible to the scan: no
              inline: probe-start appears, and the summary's discovered bucket counts
              only the raw input —
              { discovered: 1, compiled: 1, failed: 0, excluded: 0 }.
            
    • 
            
  • 
              The raw probe still matched the live stage element, and its resolved color is
              rgb(6, 6, 6) — the color the unscanned inline style painted,
              because the browser applies that style regardless of what the scan collects. The scan
              ignoring a source never turns it off.
            
    • 
          

        

      

    


    

      

        
4.3 An empty raw id is rejected, with its index

        
        
      

      

        
<p class="raw-target"></p>

        
[
  { "id": "named", "css": "/* css-console: log color */\n.raw-target { color: rgb(1, 2, 3); }" },
  { "id": "", "css": ".dropped { color: red; }" }
]

        

          Expected
          
    
            
  • 
              One EMPTY_SOURCE_IDENTITY diagnostic, error severity, details
              index: 1 — the position in the supplied list, because an empty string
              cannot itself name which input failed.
            
    • 
            
  • 
              The empty-id input produces no source at all; css-console never generates a fallback
              name for a raw source, because the caller is naming their own object, not an anonymous
              document node.
            
    • 
            
  • 
              Summary sources: { discovered: 2, compiled: 1, failed: 1, excluded: 0 }.
            
    •

<style data-css-console-source="tokens">
/* css-console: log color */

</style>
<p class="cross-a"></p><p class="cross-b"></p>

              differ (inline:tokens and raw:tokens); it is the identity
              that collides.
            
    • 
            
  • Both sources still compile and both records arrive.

5. Gating and exclusion

    

      Discovery reports every source; the gate then sorts them into active, inactive, and excluded.
      Inactive means the browser is not reading the source right now — a non-matching
      media attribute, or a sheet disabled through the IDL property. Excluded is the
      caller's own decision, by URL pattern: * matches within a path segment,
      ** crosses /, everything else is literal, and a pattern without a
      wildcard is an exact match. The synthesized inline: and raw: URLs
      are excludable like any other.
    


    

      

        
5.1 A print-media style is discovered but inactive

        
        
      

      

        
<style media="print">
/* css-console: log color */
.print-only { color: rgb(9, 9, 9); }
</style>
<style>
/* css-console: log color */
.screen-too { color: rgb(1, 1, 1); }
</style>
<p class="print-only screen-too"></p>

        

          Expected
          
    
            
  • 
              Only the second style produces events. The print style is counted in
              discovered and in no other bucket — the gap between
              discovered and the other three buckets is the inactive sources.
            
    • 
            
  • 
              Summary sources: { discovered: 2, compiled: 1, failed: 0, excluded: 0 }.
            
    • 
          

        

      

    


    

      

        
5.2 The disabled attribute is inert; the IDL property is real

        
        
      

      

        

          Steps
          
    
            
  1. Load and run: the style scans despite its disabled attribute.
    2. 
            
  2. Press Disable first fixture style (IDL), then run again.
    3. 
          

        

        
<style disabled>
/* css-console: log color */
.maybe-disabled { color: rgb(3, 1, 4); }
</style>
<p class="maybe-disabled"></p>

        

          Expected
          
    
            
  • 
              Run 1: the probe evaluates and the element renders in rgb(3, 1, 4). A
              disabled attribute on a style element does nothing in the engine
              — pinned in the browser suite — so the gate, which reads what the engine reads, treats
              the sheet as active.
            
    • 
            
  • 
              Run 2: after element.disabled = true (the IDL property, which is real),
              the stage element loses its color, the style is inactive, and the summary is
              { discovered: 1, compiled: 0, failed: 0, excluded: 0 } with no probe
              events.
            
    • 
          

        

      

    


    

      

        
5.3 Exclusion by pattern, across all three source kinds

        
        
      

      

        
<style data-css-console-source="keep-me">
/* css-console: log color */
.kept { color: rgb(1, 2, 3); }
</style>
<style data-css-console-source="drop-me">
/* css-console: log color */
.dropped { color: rgb(4, 5, 6); }
</style>
<link rel="stylesheet" href="/manual-testing-phase3.css?direct">
<p class="kept dropped linked-probe"></p>

        
{ "exclude": ["inline:drop-me", "**/manual-testing-phase3.css*"] }

        

          Expected
          
    
            
  • 
              Only inline:keep-me produces events. inline:drop-me is an
              exact-match exclusion (no wildcard, whole-URL match); the link is excluded by a
              ** pattern that crosses path segments, with a trailing
              * because the fixture URL carries the ?direct query.
            
    • 
            
  • 
              The one record resolves color: rgb(20, 40, 60) — the
              linked stylesheet's color, not the probed rule's rgb(1, 2, 3).
              Exclusion stops scanning, not application: the engine still loads and applies the link
              element. And the guard reports the value uncontested, because the guard reads compiled
              CSS and a source the caller excluded is never compiled — its declarations are
              invisible to the guard. Excluding a source narrows what a report can explain.
            
    • 
            
  • 
              The excluded link is never fetched — confirm in the network panel that no request for
              the stylesheet leaves the page.
            
    • 
            
  • 
              Summary sources: { discovered: 3, compiled: 1, failed: 0, excluded: 2 }.

6. Failure isolation

    

      Fault isolation is by source: one unparseable stylesheet, one failing request, or one rejected
      raw input produces a diagnostic and costs nothing else. The composite scenario at the end
      exercises every summary bucket in one scan, mirroring the browser suite's own six-candidate
      fixture.

<style>
.broken {
</style>
<style>

</style>
<p class="intact"></p>

              One SOURCE_PARSE_FAILED diagnostic, error severity, carrying the parser's

    •

              Summary sources: { discovered: 2, compiled: 1, failed: 1, excluded: 0 }.

7. The scan lifecycle

    

      Scans on one instance are serialized; an abort rejects with the engine's own
      AbortError and emits no summary; maxElements truncates visibly; and
      a disposed instance refuses further work while a scan already in flight still settles.
    


    

      

        
7.1 Overlapping scans are serialized

        
        
      

      

        

          Steps
          
    
            
  1. 
              Load, then press Run two scans (it calls scan() twice
              without awaiting the first).
            
    2. 
          

        

        
<style>
/* css-console: log color */
.serialized { color: rgb(7, 7, 7); }
</style>
<p class="serialized"></p>

        

          Expected
          
    
            
  • 
              Two complete event sequences, one after the other: the second scan's
              probe-start comes after the first scan's summary. Nothing
              interleaves, so a subscriber can always tell which scan a record belongs to.
            
    • 
          

        

      

    


    

      

        
7.2 An abort rejects the scan and delivers no summary

        
        
      

      

        

          Steps
          
    
            
  1. 
              Load, then press Run + abort (it calls scan() and aborts
              the controller immediately).
            
    2. 
          

        

        
<style>
/* css-console: log color */
.aborted { color: rgb(6, 6, 6); }
</style>
<p class="aborted"></p>

        

          Expected
          
    
            
  • 
              The scan promise rejects with AbortError (shown as a rejection line in
              the output) and no summary event appears. An abort is the caller's
              decision, not a finding about the document, so it produces no diagnostic either.

7.5 A disposed instance refuses further work

        
        
      

      

        

          Steps
          
    
            
  1. Load and run once normally.
    2. 
            
  2. Press Dispose instance, then Run scan again.
    3. 
          

        

        
<style>
/* css-console: log color */
.disposable { color: rgb(2, 2, 2); }
</style>
<p class="disposable"></p>

        

          Expected
          
    
            
  • 
              The second run reports a thrown error (the harness shows it as an error line) —
              scan() on a disposed instance throws rather than scanning. Press
              New instance to continue.
            
    •
