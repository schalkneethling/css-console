The css-console playground

Nine annotated declarations, nine questions the CSS source cannot answer on its own, and one browser console report that answers all of them.

How to read this page

css-console turns a comment in your CSS into a live report about what the browser actually resolved. Every case below is annotated in examples/playground/playground.css, the one stylesheet this page links, and every annotation follows the same grammar: css-console: <log-level> [property-list] [label="..."].

  1. Serve the repository with vp dev, and open this page at /examples/playground/index.html.
  2. Open the browser console, and reload the page.
  3. Expand the group whose title carries the label of the case you are reading, for example [case-1].

A group title names the source, the line, the column, and the selector the engine resolved. Inside the group, each line reads property: authored value → resolved value, so the value you wrote and the value the browser computed sit beside each other. A value that ends in (contested) carries a second line, the handoff, which names the reason another declaration may have contributed to what you are seeing and hands the question to your developer tools. The report never claims a winner, because the guard reports facts rather than resolving the cascade for you.

Case 1 A custom function, resolved at every call site

A custom function has no value of its own. It has a result, and the result exists only where the function is called, on the element that called it. Reading @function --case-1-step() tells you the arithmetic, and tells you nothing about the numbers, because the numbers arrive from the custom property each matched element carries. This function is called from two properties in two rules, so it produces two call sites, and one of those call sites matches three elements that disagree about the unit.

--case-1-unit: 8px
--case-1-unit: 12px
--case-1-unit: 16px

The second call site is the padding on this paragraph, driven by a smaller unit.

In the console: one group titled [case-1] --case-1-step, holding one collapsed group per call site. Each call-site group names the destination property, the arguments as authored, and the selector, and holds one table of the resolved property values, one row per matched element.

The source

/* css-console: log label="case-1" */
@function --case-1-step(--n) {
  result: calc(var(--case-1-unit) * var(--n));
}

.case-1-unit-8 { --case-1-unit: 8px; }
.case-1-unit-12 { --case-1-unit: 12px; }
.case-1-unit-16 { --case-1-unit: 16px; }

.case-1-bar {
  inline-size: --case-1-step(3);
}

.case-1-note {
  --case-1-unit: 6px;

  padding-inline-start: --case-1-step(2);
}

Case 2 A color mix, resolved once per theme

The two declarations below are character for character identical, and they paint different colors, because each one mixes a brand color its own section supplies. The authored value names a mixing space, a percentage, and a variable, and the color you see is none of those three: it is the result the engine computed in oklch and then serialized. The report shows the mix as you wrote it and the concrete color it became.

Warm theme

Cool theme

In the console: two groups titled [case-2], one per themed selector. Each holds a single line carrying a color swatch, the authored color-mix(), and the resolved color, and neither resolved color contains a variable or a mix function any more.

The source

.case-2-warm { --case-2-brand: oklch(0.68 0.18 45); }
.case-2-cool { --case-2-brand: oklch(0.62 0.16 250); }

/* css-console: log background-color label="case-2" */
.case-2-warm .case-2-chip {
  background-color: color-mix(in oklch, var(--case-2-brand) 60%, white);
}

/* css-console: log background-color label="case-2" */
.case-2-cool .case-2-chip {
  background-color: color-mix(in oklch, var(--case-2-brand) 60%, white);
}

Case 3 A container unit, resolved against its container

A cqi length is one percent of the inline size of the nearest query container, so a single declaration has as many values as it has containers. The source names a fraction, never a size, and the size belongs to an ancestor the declaration does not mention. The two captions below share one rule and live in containers of different widths.

Wide container

Narrow container

In the console: one group titled [case-3] .case-3-caption, holding a table with one row per caption. The authored column reads 6cqi in both rows, and the resolved column reads two different pixel values.

The source

.case-3-container {
  container-type: inline-size;
}

.case-3-wide { inline-size: 32rem; }
.case-3-narrow { inline-size: 14rem; }

/* css-console: log font-size label="case-3" */
.case-3-caption {
  font-size: 6cqi;
}

Case 4 A clamp, at both bounds and between them

A clamp() has three regimes, and a declaration tells you which three values are involved without telling you which regime any element is in. The fluid middle here is a per-element custom property rather than a viewport length, so all three regimes are visible at once, at any window size: the first bar is pinned at the lower bound, the second is genuinely fluid, and the third is pinned at the upper bound.

--case-4-pull: 2rem
--case-4-pull: 13rem
--case-4-pull: 40rem

The first bar and the third bar ignore their custom property entirely, which is the whole point of a bound.

In the console: one group titled [case-4] .case-4-bar, holding a table of three rows. Every row repeats the same authored clamp(), and the resolved column shows the lower bound, a value strictly between the bounds, and the upper bound.

The source

.case-4-pull-low { --case-4-pull: 2rem; }
.case-4-pull-mid { --case-4-pull: 13rem; }
.case-4-pull-high { --case-4-pull: 40rem; }

/* css-console: log inline-size label="case-4" */
.case-4-bar {
  inline-size: clamp(6rem, var(--case-4-pull), 24rem);
}

Case 5 A custom property, at the end of its inheritance chain

The leaf declaration below reads var(--case-5-tone) and stops there. Which declaration of --case-5-tone reached any particular leaf is a question about the tree the leaf sits in, not about the rule, and a stylesheet that declares the property in several places cannot answer it by inspection. Both leaves match the same rule, and only one of them inherits the value declared halfway down.

A leaf directly under the root, which declares the tone.

A leaf under a branch, which declares the tone again.

In the console: one group titled [case-5] .case-5-leaf, holding a table with one row per leaf. Both rows were authored as var(--case-5-tone), and the resolved colors differ, because the value that arrived differed.

The source

.case-5-root { --case-5-tone: oklch(0.55 0.15 250); }
.case-5-branch { --case-5-tone: oklch(0.52 0.19 25); }

/* css-console: log color label="case-5" */
.case-5-leaf {
  color: var(--case-5-tone);
}

Case 6 A pseudo-element sized by its generated content

A ::before pseudo-element has no element in the document, so it cannot be selected, inspected, or measured the way an element can. Its content comes from an attribute, and its width follows from that content, which means the width lives in the markup, in the font, and in the layout, and nowhere in the declaration. css-console reads the pseudo-element directly and reports what it measured.

In the console: one group titled [case-6] .case-6-tag::before, holding a table with one row per tag. The authored column reads max-content every time, and the resolved widths grow with the label the attribute supplied.

The source

/* css-console: log width label="case-6" */
.case-6-tag::before {
  content: attr(data-tag);
  width: max-content;
}

Case 7 A random value, behind a feature query

The random() function returns a value the source cannot state by definition, and it is new enough that a browser may not implement it at all. The declaration is therefore guarded by @supports (width: random(1px, 2px)). That guard is worth watching for its own sake: css-console evaluates a rule's conditions against the live engine, so where the feature query fails the group still opens, from the source, and reports nothing, because nothing applied.

This browser does not support random(), so the guarded declaration never applied, the bars above have no width of their own, and the console group for this case is empty. That empty group is the report: the rule exists in the source, and this engine is not using it.

In the console: one group titled [case-7] .case-7-die. In an engine that supports random() it holds one resolved width per bar. In an engine that does not, it holds nothing at all.

The source

@supports (width: random(1px, 2px)) {
  /* css-console: log width label="case-7" */
  .case-7-die {
    width: random(4rem, 12rem);
  }
}

.case-7-notice { display: none; }

@supports not (width: random(1px, 2px)) {
  .case-7-notice { display: block; }
}

Case 8 A nested rule, and the selector it resolves to

CSS nesting substitutes the parent rule into the child through :is(), which preserves matching behavior and specificity, and produces a selector no line of the source contains. Two levels of nesting are enough for the resolved selector to stop resembling anything you wrote. css-console resolves nesting before it matches, so the group title is the selector the engine used rather than the spelling the stylesheet carries.

In the console: one group titled [case-8] whose selector is a nest of :is() wrappers. Compare it to the three lines of source below, and note that the title appears in neither.

The source

.case-8-panel {
  .case-8-row {
    /* css-console: log border-color label="case-8" */
    .case-8-dot {
      border-color: oklch(0.62 0.19 25);
    }
  }
}

Case 9 A shorthand competing with an annotated longhand

The rule below sets margin-left, and then sets margin, which sets margin-left again. A report that showed only the annotated declaration and the resolved value would be quietly misleading, because the resolved value did not come from the annotated declaration. The guard exists for exactly this: it reports that the annotated declaration may not be the sole contributor, names why, and hands you the live element. It never names a winner, because deciding the cascade is the job of your developer tools.

This card is annotated to report margin-left: 3rem, and it is sitting at a margin of 0.5rem.

In the console: one group titled [case-9] .case-9-card, holding a line that ends in (contested), followed by a handoff line reading contested (competing-declaration) and the instruction to inspect the element. The live element travels with that line, so clicking it in the console takes you to the box the report is about.

The source

/* css-console: log margin-left label="case-9" */
.case-9-card {
  margin-left: 3rem;
  margin: 0.5rem;
}
