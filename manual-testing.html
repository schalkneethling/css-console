css-console — Phase 2 manual testing

A hands-on checklist for the real-browser evaluator that landed with CSSC-017 through CSSC-023: condition evaluation, selector matching, resolved value reading, function probes, the contested guard, match limits, and the normalized event stream.

How to use this document

The project has no public runtime entry point yet: createCSSConsole() is CSSC-028, and the console adapter is Phase 4. Until then, the pipeline is exercised by composing compileSource() with evaluateSource(), which is exactly what this page does. It works in two modes:

  • Live mode. Serve the project and open this file through the dev server. The playground below then imports the modules straight from src/ and runs real scans against fixtures on this page: 
    vp dev
# then open http://localhost:5173/manual-testing.html
  • Reading mode. Opened directly from disk, the playground disables itself and the document reads as a plain checklist. Every scenario carries its own CSS, markup, and expected outcome, so it can also be reproduced in a scratch browser-lane test under test/browser/.
Every expected value in this document was pinned against headless Chromium 151.0.7922.34, the engine the browser test lane runs. Chrome of a similar version should agree. Firefox and Safari will differ where noted, and observing those differences is itself useful manual testing; the most visible one is that @function probes evaluate only where CSSFunctionRule exists. Each scenario has a checkbox; ticks persist in this browser's localStorage.

1. Value probe basics


    

      

        
1.1 One annotation produces one record

        
        
      

      

        
/* css-console: log color */
.solo { color: rgb(1, 2, 3); }

        
<p class="solo">probe me</p>

        

          Expected
          
    
            
  • 
              Event order: probe-start, record,
              probe-summary.
            
    • 
            
  • 
              The record's color resolves to rgb(1, 2, 3), authored value
              preserved.
            
    • 
            
  • Guard: contested: false, no reasons.
    • 
            
  • 
              Summary: 1 record, 0 diagnostics, matches
              { total: 1, evaluated: 1, omitted: 0 }.
            
    •

/* css-console: log color */
.plain { color: rgb(8, 8, 8); }

        
<p class="tagged"></p><p class="plain"></p>

        

          Expected

    • 
            
  • 
              The second probe's events have no label key at all (check the raw JSON:
              the key is absent, not undefined).

3. Conditions


    

      

        
3.1 An inactive probe still has boundaries

        
        
      

      

        
@media (min-width: 100000px) {
  /* css-console: log color */
  .unreachable { color: rgb(1, 1, 1); }
}

        
<p class="unreachable"></p>

        

          Expected
          
    
            
  • 
              probe-start and probe-summary are emitted, with zero records
              and matches { total: 0, evaluated: 0, omitted: 0 }.
            
    • 
            
  • No record events: the condition never holds in any real viewport.
    • 
          

        

      

    


    

      

        
3.2 Conditions are read live, never cached

        
        
      

      

        
@media (min-width: 600px) {
  /* css-console: log color */
  .responsive { color: rgb(2, 2, 2); }
}

        
<p class="responsive"></p>

        

          Steps: run the scan with the window wider than 600px, then resize the
          window below 600px and run again without reloading.
        

        

          Expected
          
    
            
  • Wide window: one record. Narrow window: zero-count boundaries only.
    • 
            
  • 
              The answer follows the viewport at the moment of each scan; nothing is remembered from
              the previous run.
            
    • 
          

        

      

    


    

      

        
3.3 @layer never gates, @supports does

        
        
      

      

        
@layer base {
  @supports (display: grid) {
    /* css-console: log color */
    .layered { color: rgb(3, 3, 3); }
  }
}

@supports (display: not-a-value) {
  /* css-console: log color */
  .unsupported { color: rgb(4, 4, 4); }
}

        
<p class="layered"></p><p class="unsupported"></p>

        

          Expected
          
    
            
  • 
              The .layered probe records: the layer is metadata, the supported
              condition holds.
            
    • 
            
  • 
              The .unsupported probe emits boundaries only: an unparseable or failing
              supports condition is inactive.

4. Selector branches


    

      

        
4.1 A branch the engine refuses fails alone

        
        
      

      

        
/* css-console: log color */
.valid-branch, .card:not-a-real-pseudo-class {
  color: rgb(1, 2, 3);
}

        
<p class="valid-branch"></p><p class="card"></p>

        

          Expected
          
    
            
  • 
              An UNPARSEABLE_SELECTOR_BRANCH diagnostic (warning) naming the rejected
              branch, carrying the rule's source location, inside the probe's boundaries.
            
    • 
            
  • 
              The .valid-branch element still produces a record: one bad branch never
              silences its siblings in the matcher.
            
    • 
            
  • 
              The reported color is the page's inherited color, not rgb(1, 2, 3) — the
              live engine drops a style rule whose selector list contains a branch it cannot parse,
              so the annotated declaration never applied, and the record reports that truthfully.
            
    • 
          

        

      

    


    

      

        
4.2 A pseudo-element after a combinator matches the right elements

        
        
      

      

        
/* css-console: log color */
.card ::before {
  color: rgb(1, 2, 3);
}

        
<article class="card"><span id="child">child<b id="grandchild">grandchild</b></span></article>

        

          Expected
          
    
            
  • 
              Records target the descendants (#child, #grandchild), never
              the .card ancestor: .card ::before means
              .card *::before.
            
    • 
            
  • 
              No diagnostics. The same holds for .card > ::before, which matches
              only #child.
            
    • 
          

        

      

    


    
5. Pseudo-elements


    

      

        
5.1 A ::before probe reads the pseudo-element's own values

        
        
      

      

        
/* css-console: log content,color,width */
.decorated::before { content: "hi"; color: rgb(4, 5, 6); width: 30px; }

        
<p class="decorated" id="origin"></p>

        

          Expected
          
    
            
  • One record targeting #origin with pseudo: "::before".
    • 
            
  • 
              content is "hi", color is
              rgb(4, 5, 6), and width is 30px: the
              pseudo-element's values, not the element's. content is an ordinary
              property here — when it computes to none, no box is generated and the
              other properties still report their computed values.
            
    • 
          

        

      

    


    

      

        
5.2 ::placeholder degrades without a placeholder — a recorded engine quirk

        
        
      

      

        
/* css-console: log color */
.host::placeholder { color: rgb(2, 2, 2); }
.host { color: rgb(1, 1, 1); }

        
<input class="host" placeholder="hi">
<input class="host">

        

          Expected
          
    
            
  • The input with a placeholder reports rgb(2, 2, 2).
    • 
            
  • 
              The input without one reports rgb(1, 1, 1) — the element's own
              color, silently attributed to ::placeholder by the engine. This is the
              one exception among the eight supported pseudo-elements and it is documented in the
              evaluator, not worked around.
            
    • 
          

        

      

    


    
6. Resolved values


    

      

        
6.1 The engine resolves; the tool reports

        
        
      

      

        
/* css-console: log width,height,margin-top,color */
.resolved {
  width: calc(100px + 50px);
  height: clamp(10px, 500px, 100px);
  margin-top: clamp(10px, 50px, 100px);
  color: color-mix(in srgb, red 50%, blue);
}

        
<p class="resolved"></p>

        

          Expected
          
    
            
  • 
              width → 150px, height →
              100px (high bound), margin-top → 50px.
            
    • 
            
  • color → color(srgb 0.5 0 0.5).
    • 
          

        

      

    


    

      

        
6.2 display: none falls back to computed values

        
        
      

      

        
/* css-console: log width,margin-left */
.hidden-box { display: none; width: auto; margin-left: 25%; }

        
<div style="width: 300px"><p class="hidden-box"></p></div>

        

          Expected
          
    
            
  • 
              width reports auto and margin-left reports
              25%: with no box, resolved values fall back to computed values, and a
              percentage stays a percentage.
            
    • 
            
  • 
              Remove display: none and re-run: margin-left resolves to
              75px (25% of the 300px containing block) and width reports
              225px. A used width: auto on a block box is the containing
              block minus margins, borders, and padding, so the margin claims its 75px first.
              box-sizing plays no part here, because it only changes how a specified
              width maps onto the box, and this width is auto. Delete the margin
              declaration too and width reports the full 300px, which is
              the shape the evaluator suite pins.
            
    • 
          

        

      

    


    

      

        
6.3 Custom properties: declared, empty, and never declared

        
        
      

      

        
/* css-console: log --brand,--declared-empty,--never-declared */
.branded { --brand: oklch(55% 0.18 250); --declared-empty: ; color: red; }

        
<p class="branded"></p>

        

          Expected
          
    
            
  • --brand reports its declared value verbatim.
    • 
            
  • 
              --declared-empty reports the empty string — an honest report of what the
              engine computes for a declared-empty custom property.
            
    • 
            
  • 
              --never-declared does not appear in the record at all: a
              MISSING_REQUESTED_PROPERTY diagnostic flags it at compile time, and the
              probe carries only the properties the rule declares.

7. The contested guard

    

      The guard answers one question per probed property and element: could something other than the
      annotated declaration be responsible for the reported value? It fires reasons as facts and
      never ranks, counts, or locates competitors.
    

    

      Expect the reasons to be facts about the probed box, never pointers to competitors: the guard
      will not say which declaration competes, how many do, or who wins, and ten
      competitors produce the same reasons array as one. That restraint is the design
      (docs/decisions/0004-guard-as-guard-not-cascade-feature.md): any identification is a claim
      about the cascade, page JavaScript cannot fully make that claim — user-agent stylesheets,
      presentational hints, and origin ordering are not observable from script — and a partially
      correct claim is worse than a handoff. The handoff is the remediation: every record carries
      the live matched element as its target, one click from the devtools cascade
      panel, which can see everything and does name the winner. Each reason is independent, so an
      important competitor fires competing-declaration and important as
      two facts, with neither attributing the value to anyone.
    


    

      

        
7.1 competing-declaration, and important beside it

        
        
      

      

        
/* css-console: log color */
.card { color: red; }
.other { color: blue !important; }

        
<p class="card other"></p>

        

          Expected
          
    
            
  • 
              Guard reasons: competing-declaration and important — two
              facts, both reported.
            
    • 
            
  • 
              Drop !important and re-run: only
              competing-declaration remains.
            
    • 
            
  • 
              Also try a shorthand competitor (.other { margin: 0 } against a probed
              margin-left) and all: initial: both compete.
            
    • 
          

        

      

    


    

      

        
7.2 inline-style, with importance carried

        
        
      

      

        
/* css-console: log color */
.card { color: red; }

        
<p class="card" style="color: blue !important"></p>

        

          Expected
          
    
            
  • Guard reasons: inline-style and important.
    • 
            
  • 
              Without !important: inline-style alone. An inline style on
              an unrelated property fires nothing.
            
    • 
          

        

      

    


    

      

        
7.3 Logical competition follows the element's flow

        
        
      

      

        
/* css-console: log inline-size */
.card { inline-size: 5px; }
.wide { width: 7px; }

        
<p class="card wide"></p>

        

          Expected
          
    
            
  • 
              Horizontal writing mode: width addresses the same physical longhand as
              inline-size, so competing-declaration fires.
            
    • 
            
  • 
              Add .card { writing-mode: vertical-rl; } to the fixture and re-run: the
              guard goes silent, because inline-size now maps to height.
            
    • 
          

        

      

    


    

      

        
7.4 animation-or-transition, on the element and on its pseudo-element

        
        
      

      

        
/* css-console: log margin-left */
.card { margin-left: 0px; animation: slide 100s linear; }

@keyframes slide { from { margin-left: 0px; } to { margin-left: 300px; } }

        
<p class="card"></p>

        

          Expected
          
    
            
  • 
              Guard reason: animation-or-transition (the scan waits a frame, so the
              animation is running).
            
    • 
            
  • 
              Move the animation into a .card::before rule, add
              content: "" beside it, and probe the pseudo-element: the reason follows
              the probed box, firing for the ::before probe and staying silent for the
              element's own probe.
            
    • 
            
  • 
              The content declaration is load-bearing, not decoration. Without it the
              pseudo-element generates no box, and an animation on a boxless pseudo-element never
              runs: getAnimations({ subtree: true }) returns nothing for it, and the
              reported margin-left stays at its static value. The guard's silence there
              is the honest answer — the value really did not come from an animation.
            
    • 
            
  • An animation on an unrelated property fires nothing.
    • 
          

        

      

    


    

      

        
7.5 unresolved-variable, in all its shapes

        
        
      

      

        
/* css-console: log color */
.a { color: var(--missing); }

/* css-console: log color */
.b { color: VAR(--missing); }

/* css-console: log color */
.c { color: var(--missing, red); }

/* css-console: log color */
.d { color: var(--missing, 10px); }

        
<p class="a"></p><p class="b"></p><p class="c"></p><p class="d"></p>

        

          Expected
          
    
            
  • 
              .a fires unresolved-variable; .b fires it
              identically, because CSS function names are case-insensitive.
            
    • 
            
  • .c stays silent: a valid fallback saves the declaration.
    • 
            
  • 
              .d fires: 10px is not a valid color, so the consulted
              fallback fails the destination.
            
    • 
          

        

      

    


    

      

        
7.6 A pseudo-element's own custom property resolves without a false alarm

        
        
      

      

        

          Custom properties cascade per element and pseudo-element pair, so a
          --tone declared only inside the ::before rule exists for the
          pseudo-element and is absent from the originating element. The guard resolves references
          against the same computed declaration the reported values came from, so asking the wrong
          box here would fire unresolved-variable for a reference the engine resolved.
        

        
/* css-console: log color */
.decorated::before {
  content: "";
  --tone: rgb(0, 128, 0);
  color: var(--tone);
}

        
<p class="decorated"></p>

        

          Expected
          
    
            
  • 
              The record reports color: rgb(0, 128, 0), uncontested: the reference
              resolved on the ::before declaration, even though
              getPropertyValue("--tone") on the element itself answers the empty
              string.
            
    • 
            
  • 
              Delete the --tone declaration, keep the var(--tone)
              reference, and re-run: now the reference genuinely fails and
              unresolved-variable fires.
            
    • 
          

        

      

    


    

      

        
7.7 Box alignment: pseudo-element probes compete per box

        
        
      

      

        
/* css-console: log color */
.decorated::before { content: ""; color: red; }
.other::before { color: blue; }
.decorated { color: green; }

        
<p class="decorated other"></p>

        

          Expected
          
    
            
  • 
              Guard reason: competing-declaration, fired by
              .other::before — a rule on the same pseudo-element box. An
              element has exactly one ::before, so every matching
              ::before rule cascades into that one box; the reported color is in fact
              blue, because the competitor wins on source order at equal specificity, which is
              exactly the situation the guard exists to flag.
            
    • 
            
  • 
              The competitor needs no content of its own — and neither rule does:
              delete both content declarations and the guard still fires, with the
              boxless ::before still reporting the cascaded blue. Box generation gates
              rendering and animation playback (see 7.4), never the cascade or the computed values.
            
    • 
            
  • 
              Remove the .other::before rule and re-run: silence. The element's own
              color: green never competes with the ::before box, which it
              reaches only through inheritance.
            
    • 
          

        

      

    


    
8. Function probes


    

      

        
8.1 An annotated @function reports its call sites

        
        
      

      

        
/* css-console: log */
@function --space(--n) { result: calc(var(--n) * 8px); }

.card { padding-top: --space(2); }
.panel { margin-top: --space(3); }

        
<p class="card"></p><p class="panel"></p>

        

          Expected
          
    
            
  • 
              One probe-start (probeKind: "function", naming --space),
              then one record per call site.
            
    • 
            
  • 
              The .card record reports padding-top resolved to
              16px, the .panel record margin-top to
              24px — always the destination property's resolved value, never the bare
              return value.
            
    • 
            
  • 
              Each record's call site carries soleContribution: true here; wrap a call
              as calc(--space(2) + 1px) and it flips to false.
            
    • 
            
  • 
              In a browser without CSSFunctionRule (Firefox, Safari at the time of
              writing), the probe reports nothing rather than guessing — worth verifying there too.
            
    • 
          

        

      

    


    
9. Match limits


    

      

        
9.1 Truncation keeps document order and the true totals

        
        
      

      

        
Set maxElements to 3 before running.

        
/* css-console: log color */
.item { color: rgb(1, 2, 3); }

        
<li class="item" id="first"></li><li class="item" id="second"></li><li class="item" id="third"></li><li class="item" id="fourth"></li><li class="item" id="fifth"></li>

        

          Expected
          
    
            
  • 
              Exactly 3 records, targeting #first, #second,
              #third in document order.
            
    • 
            
  • 
              Summary matches: { total: 5, evaluated: 3, omitted: 2 } — nothing about
              the page is hidden by the limit.
            
    • 
            
  • 
              maxElements: 0 evaluates nothing while still counting
              total: 5.
            
    • 
          

        

      

    


    

      

        
9.2 A function probe spends one budget across call sites

        
        
      

      

        
Set maxElements to 4 before running.

        
/* css-console: log */
@function --pad(--n) { result: calc(var(--n) * 1px); }

.first { padding-top: --pad(1); }
.second { margin-top: --pad(2); }

        
<p class="first"></p><p class="first"></p><p class="first"></p><p class="second"></p><p class="second"></p><p class="second"></p>

        

          Expected
          
    
            
  • 
              4 records: three for the first call site, one for the second — the budget is
              probe-wide, not per call site.
            
    • 
            
  • Summary matches: { total: 6, evaluated: 4, omitted: 2 }.

10. The event stream


    

      

        
10.1 Ordering, determinism, and the read-only guarantee

        
        
      

      

        
/* css-console: log color,ghost */
.first-probe { color: rgb(1, 1, 1); }

/* css-console: log color */
.second-probe { color: rgb(2, 2, 2); }

        
<p class="first-probe"></p><p class="second-probe"></p>

        

          Expected
          
    
            
  • 
              Compilation diagnostics come first, then each probe's probe-start →
              records → probe-summary, in authored order.
            
    • 
            
  • 
              Run twice: the probeId values and the event order are identical across
              runs.
            
    • 
            
  • Timestamps never decrease within a run.
    • 
            
  • 
              Inspect the stage in devtools before and after a run: the markup is untouched — every
              engine call the pipeline makes is a read.
            
    • 
          

        

      

    


    
11. Known false negatives — expect silence here

    

      Three guard misses are recorded decisions, not defects. Verifying them means confirming the
      guard stays silent:
    

    

      

        Fixture
        Why the guard cannot see it
      

      

        
          A competitor inside @container, @scope, or
          @starting-style
        
        
          Those at-rules cannot be honestly probed, so their declarations never enter the guard
          index.
        
      

      

        
          A keyframes animation on a custom property (registered through @property or
          not)
        
        
          getKeyframes() in Chromium 151 omits custom properties from its keyframe
          objects, even when the property animates as a typed interpolation.
        
      

      

        A competitor whose selector the engine cannot parse
        
          matches() throws on it, and a selector the engine cannot evaluate is a
          selector the engine cannot be applying.
        
      

    

    

      One neighboring scope decision: a var() reference whose variable is
      set clears unresolved-variable even when the set value is invalid for
      the destination. The reason is about references that fail, not values that disappoint.
